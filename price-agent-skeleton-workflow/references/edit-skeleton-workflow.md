# 修改提示词

对任意提示词写操作，只要 `promptVersionId>0` 就进入本流程并基于当前版本派生新草稿；用户具体使用新建、创建、初始化、重新生成、修改、优化、调整、增删或按照规则生成等哪一种说法都不影响路由。共享步骤见 [shared-steps.md](shared-steps.md)。

> **命中即执行**：同一轮执行到 `[S3]` 和提案；用户说“新建”仍是基于当前版本派生草稿，`writeMode=EDIT`。

> **无验证数据直达**：用户没有提供或要求 Badcase、验证任务、验证结果、分析验证集时，直接按本流程处理。这些数据不是进入 EDIT 的前置条件，不调用相关 MCP，也不因缺少它们而停止或澄清。

> **无方向普通修改**：立即查询当前 `promptVersionId`，不得询问 ID、名称或方向。基础正文结构合规时，
> 只依据正文现有内容按 `skeleton-format.md` 修复格式、歧义、重复、矛盾、术语、Step 和 JSON 约束，
> 不执行 `[S2]`，不加载当前比价项、母子品牌或材质关系，也不启用全量同步门禁；不得借机补写或
> 改写业务规则、阈值和映射。只有命中“格式重构硬分支”时，才因无法保留完整正文而执行 `[S2]`。

> **格式重构硬分支**：查询到的本轮 `promptContent` 只要明显不符合 `skeleton-format.md`，例如仅为
> `1`、`111`、短句、占位内容，或缺少固定章节、真实比价项、映射格式、图片说明、完整 JSON 输出
> 约束，就必须在本轮加载 `[S2]` 的真实规则与映射，并重构为符合 `skeleton-format.md` 的完整提示词。
> 这本身就是“优化/改善/修改提示词”的执行目标，不得询问用户优化方向，不得保留残缺结构、虚构
> “核心比价项”或先提交残缺原文。精确修改仅在基础正文足以定位并保留业务规则时才可跳过 `[S2]`；
> 基础正文无法支撑完整重构时，本分支优先，必须执行 `[S2]`。

> **残缺正文不是外部依赖错误**：`promptContent` 为 `1`、`111` 或其他残缺内容时，禁止声称“未找到
> 编辑/初始化流程配置”，禁止要求用户复制、补充或粘贴原骨架，也禁止提供“人工粘贴使用”的草稿。
> 本文件就是 EDIT workflow；`promptVersionId>0` 时不得查找或依赖 INITIALIZE workflow。必须继续
> 读取下方 references、执行 `[S2]`，并以真实 MCP 数据重构。只有某个必读 reference 实际读取失败
> 时才停止，且只能报告该文件的准确路径和真实读取错误，不得用泛化的“配置缺失”代替。

> **compareLogic 单一事实源**：凡涉及比价项匹配生成，必须完整读取 [enums.md](enums.md) 的
> “比价项匹配逻辑”一节；禁止从其他 reference 的局部描述拼装、缩写或补全枚举语义。

> **精确修改直达分支**：用户给出可唯一定位的增删改时，将其作为已授权修改目标。基础正文结构
> 可用时不执行 `[S2]`，不调用关系、规则或验证任务 MCP 复核；若命中“格式重构硬分支”，则必须
> 执行 `[S2]` 重构完整正文。单个母子品牌或材质关系的新增、删除、替换及成员调整均属于此分支。
> 正文格式合规时只做该修改及其必需的机械一致性调整；品牌、材质、比价项的结构和机械一致性统一
> 执行 [rule-transformation-guide.md](rule-transformation-guide.md)，本文件不重复展开。`writeMode`
> 始终为 `EDIT`。

> **EDIT 意图识别优先级**：先判断用户是否给出可唯一定位的具体增删改，再判断是否要求依据规则或
> 关系做全量同步，最后才是无方向普通修改：
>
> 1. 用户明确给出要新增、删除、替换的材质关系、母子品牌关系、比价项、规则句、章节或其他具体
>    内容时，固定进入“精确修改直达分支”。即使句中同时出现“规则”“品牌”“材质”，也不得升级为
>    当前规则全量同步分支。
> 2. 用户没有给出可唯一定位的具体改动，而是要求“根据/按照/通过当前或最新的比价项规则、母子品牌
>    关系、材质规则更新/同步/优化提示词”或等价表达时，才进入“当前规则全量同步分支”。
> 3. 仅说“修改提示词”“优化提示词”等，既无具体改动也未要求依据规则或关系同步时，进入“无方向
>    普通修改”，不得自动启用全量同步门禁。
>
> “母子品牌”按完整业务词识别；不得将“母婴”类目或包含“母婴”的普通文本误识别为母子品牌关系。
> 一次请求只能锁定一个分支，后续规则或工具响应不得改变已锁定分支。

> **当前规则全量同步分支**：用户要求“根据/按照目前、当前、最新的比价项规则、母子品牌、材质等
> 更新/优化提示词”或等价表达时，属于非精确修改，并锁定
> `editTargetScope={priceRules:true,brand:按真实比价项门禁,material:按真实比价项门禁}`。不得把
> “比价项规则”降级为查询依据或只更新映射表。必须按本轮 `[S2]` 结果逐项重建并核对全部真实
> `ruleTableInfo[]` 比价项、品牌映射和材质映射；某项与基础提示词一致时可以不产生 Diff，但必须有
> 逐项核对记录，禁止未经核对就在提案中声称其“保持不变”。

> **EDIT 目标覆盖门禁**：上述分支生成候选全文前，建立内部 `editCoverageLedger`，这不是候选提示词
> 正文，禁止复制、改写或概括到 `promptContent`。对每个真实 `ruleTableInfo[]` 依次记录：
> `compareItem`、`cateNameTree`、原始 `infoSource`、稳定投影后的 `expectedPriority`、候选优先级、
> 该项完整特殊规则、真实 `compareLogic`、`expectedMatch`、候选全部匹配条件、基础正文对应内容、
> 候选正文对应内容、是否发生变更及原因。只有每项都有候选落点，优先级与 `expectedPriority` 完全
> 一致，且候选匹配与 `expectedMatch` 逐项一致并已包含“特殊规则 + 兜底规则”，才算
> `priceRules` 覆盖完成；只查询规则、只在合理性判断中引用规则、
> 只修改映射表或笼统写“其他比价项不变”均不算完成。

> **转换与映射覆盖门禁**：当前规则全量同步分支必须完整执行
> [rule-transformation-guide.md](rule-transformation-guide.md) 的比价项集合、适用类目、优先级、匹配、
> 品牌和材质全部硬校验；关系查询与响应校验按
> [rule-loading-policy.md](rule-loading-policy.md) 执行。本文件不建立第二套类目、品牌或材质规则。

> 上述 `editCoverageLedger`、适用类目表逐行校验、品牌与材质双向门禁以及“保持不变”的逐项证明，
> 只适用于“当前规则全量同步分支”，不适用于“精确修改直达分支”或“无方向普通修改”。精确修改
> 只执行用户指定的局部变更、定位/重复检查、必要机械一致性调整、候选全文结构校验和真实 S3；不得
> 为执行这些全量门禁而调用 `[S2]`、扩展修改范围、撤销用户明确新增内容或改写未指定业务规则。

> **直达不等于直接回复**：精确修改仅在基础正文结构可用时跳过 `[S2]`；仍必须完成本文件读取、基础版本查询、完整
> 候选正文、真实 `[S3]` 校验和下方固定提案。禁止在工具校验前输出“已删除/已修改”、Markdown
> 内容片段或保存确认话术。

## 必读

所有 EDIT 都完整读取 [shared-steps.md](shared-steps.md)、[base-version-policy.md](base-version-policy.md)、
[skeleton-format.md](skeleton-format.md) 和
[rule-transformation-guide.md](rule-transformation-guide.md)。只有格式重构硬分支、当前规则全量同步分支
或 workflow 明确要求执行 `[S2]` 的其他分支才读取
[rule-loading-policy.md](rule-loading-policy.md)；结构合规的精确修改和无方向普通修改禁止仅因“必读”
加载规则或关系。当候选需要生成、替换或校验比价项匹配语义时，还必须完整读取
[enums.md](enums.md)。随后按下列顺序执行，首条可见回复只能是提案或明确错误。
`promptVersionId>0` 的本流程不读取 [initialize-skeleton-workflow.md](initialize-skeleton-workflow.md)。
任一必读文件读取失败时，明确错误必须包含失败文件名和工具返回原因；禁止要求用户提供提示词正文。

## 查询与判断

1. 重新读取本轮业务上下文 `promptVersionId`；不得使用进入 workflow 前缓存的值、上一轮值或任何
   工具返回的新版本 ID。该值不大于 0 时停止并按入口重新路由 INITIALIZE。
2. 仅当业务上下文缺少 `ruleGroupId` 时执行 `[S1]`；已有则跳过。
3. 按 [base-version-policy.md](base-version-policy.md) 查询基础版本；仅当响应中的版本 ID 等于本轮
   `promptVersionId` 时记录 `selectedPromptVersionId=本轮 promptVersionId` 并锁定 `writeMode=EDIT`，
   不等则报告查询数据错误并停止。
4. 按 [skeleton-format.md](skeleton-format.md) 完整审计本轮查询所得 `promptContent`。仅含数字、短句、
   占位内容，或缺任一固定主体章节、真实比价项和完整输出约束时，立即锁定“格式重构硬分支”；
   不得等待用户补方向，也不得把残缺原文直接提交 `[S3]`。
5. 不调用验证任务或验证结果查询；需要分析验证数据时改走用户明确触发的 Badcase 流程。
6. 格式重构硬分支和当前规则全量同步分支按 `[S2]` 加载真实规则与必要映射；无方向普通修改在
   基础正文结构合规时必须跳过 `[S2]`，精确修改在基础正文结构可用且目标可唯一定位时也必须跳过。
   只有用户明确点名的比价项无法对应规则或基础正文
   时才澄清；无方向优化、残缺正文或正文中没有比价项均不得触发澄清。
7. 精确修改和结构合规的无方向普通修改只检查各自目标、必要机械一致性和候选全文结构，不执行 `editCoverageLedger`、适用
   类目表逐行校验、品牌/材质双向门禁或未改规则逐项证明；格式重构和全量同步分支再依据规则、映射和基础正文判断
   合理性。命中“当前
   规则全量同步分支”时必须建立并完成 `editCoverageLedger`，不得因基础正文格式合规或追求最小 Diff
   而跳过逐项同步。发现冲突、关键条件缺失或误判风险时说明并停止。
8. 格式合规时做最小修改；格式重构硬分支必须按 [skeleton-format.md](skeleton-format.md) 生成完整
   标准正文并合入用户修改。保留基础正文中可识别且不冲突的业务规则；没有可保留内容时完全依据
   `[S2]` 的可信规则生成，不得要求外部补骨架。仅需范式时仍只读取 `skeleton-format.md` 对应章节，
   禁止读取 `rule-writing-examples.md` 或历史完整提示词补规则。全文按格式规范控制在 1 万字内；基础正文已
   超出时不借机大幅删减。
9. 修改涉及母子品牌表时，完整执行 [rule-transformation-guide.md](rule-transformation-guide.md)“品牌”
   小节的格式、过滤、数量和机械重编号校验；任一条件不满足时禁止调用 S3。
10. 当前规则全量同步分支在调用 `[S3]` 前执行目标覆盖硬校验：
    - `editCoverageLedger` 中真实比价项数量、名称、顺序与 `ruleTableInfo[]` 完全一致；
    - 候选全文通过 `rule-transformation-guide.md` 的全部硬校验；
    - 用户请求的每个目标均记录为“已修改”“已核对且一致”或“按真实比价项门禁不适用”，不得静默
      忽略。其中“已核对且一致”必须有基础正文与候选正文的逐项对照记录支持。
    任一项不满足都不得调用 `[S3]`，不得形成只修改映射表的不完整提案。
11. 完成上述动作后按 `[S3]` 校验，不向用户展示全文；未重构的残缺原文不得作为候选。

## 提案

按 `[S4]` 展示。以下不是示例，而是唯一允许的可见回复协议；必须逐项、按序套用。回复第一行
必须是 `## 提示词修改提案`，模板前后不得添加说明、结论、寒暄或工具执行摘要。

````markdown
## 提示词修改提案
- Agent：`<名称；查不到时写ID>`
- 基础提示词：`<名称>`（ID：`<ID>`）
- 当前提示词来源：页面左侧选定的提示词（以当前业务上下文 `promptVersionId` 为准）
- 修改建议 ID（diff_id）：`<原样引用 S3 返回的非零 data.diffRecordId>`
- 状态：尚未保存
### 合理性判断
- 修改目标：<用户的原始要求或优化方向>
- 规则与映射依据：<支持本次修改的规则依据>
- 影响与风险：<适用范围、冲突和需要回归的项>
- 不修改部分：<明确保留未改动的规则>
### Diff
```diff
<原样引用 S3 返回的 data.diffContent>
```
完整提示词已生成并通过格式校验，未在此展开。需查看请回复「展开完整提示词」。
以上仅为修改提案。确认后创建新提示词草稿，不覆盖基础版本。
确认无误请回复：**确认创建提示词草稿**。
````

### 输出硬校验

发送前逐项检查；任一项不满足就在内部重组回复，不向用户展示错误版本：

1. 必须保留模板中的标题、字段、顺序和四条「合理性判断」，不得改成自由说明文。内容可简短，
   但不得省略「影响与风险」或「不修改部分」。精确修改的依据写“用户明确指定”，不得声称来自
   未调用的 MCP。
2. `### Diff` 后必须紧跟语言标记为 `diff` 的代码围栏，禁止使用 `text`、`markdown` 或无语言围栏。
3. 围栏内容必须逐字符复制同次 S3 的 `data.diffContent`，保留每行开头的 `+`、`-`、空格、
   标题和顺序；不得摘要、解释、改写、补行、删行、重新编号或只展示“保留项”。以空格开头的
   上下文行不是新增/删除，不得据此声称“仅保留该条”。
4. 只有非零 `diffRecordId` 才能形成提案。除用户明确要求展开全文外，只输出上述模板；禁止在
   模板前后追加完整提示词、分段全文、内部推理或“已删除/已校验”等二次结论。
5. 仅当前规则全量同步分支的“修改目标”必须覆盖比价项规则、品牌和材质三个请求维度，并按真实门禁
   说明结果；“规则与映射依据”必须反映本轮逐项规则及实际调用的映射，“不修改部分”只能列出
   `editCoverageLedger` 已证明与当前规则一致的具体内容。若服务端 Diff 只包含映射变化，则必须已
   逐项证明所有比价项规则完全一致；否则禁止展示该提案。
6. 精确修改提案只陈述用户明确指定的局部目标及必要机械调整；不得声称执行了未触发的全量规则、
   适用类目、品牌或材质核对，也不得因未生成 `editCoverageLedger` 而阻止展示已经通过 S3 的局部 Diff。

## 确认后

紧邻确认时执行 `[S5]` 的 EDIT 路径。
