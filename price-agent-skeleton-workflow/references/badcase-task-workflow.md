# 验证任务 Badcase 分析

共享步骤见 [shared-steps.md](shared-steps.md)。

进入本流程立即锁定 `badcaseMode=TASK`；继续分析、整合和工具响应均不得修改该值。

## 必读

完整读取 [badcase-processing-workflow.md](badcase-processing-workflow.md)、
[badcase-attribution-policy.md](badcase-attribution-policy.md)、[rule-loading-policy.md](rule-loading-policy.md)
和 [shared-steps.md](shared-steps.md)，再连续执行统一流程 `[B0]`～`[B8]`。只有整合结果存在提示词
规则缺陷时，再读取 [edit-skeleton-workflow.md](edit-skeleton-workflow.md) 的 Diff 与确认门禁。本批验证
结果、基础版本、去重后的类目规则、必要映射、CDN 和 S3 均由统一流程查询或执行；本入口只维护
服务端续批凭证、分批/整合状态和固定输出，不得重复调用或改写查询参数。任一必读文件读取失败时，只返回
准确文件名和真实读取错误。

- 缺少任务 ID：只询问该标识。`promptVersionId<=0` 时不向用户索取 ID，只提示先在页面左侧
  选择本次验证任务使用的提示词后重试。
- 本批查询成功：当轮必须输出完整阶段分析；还有数据时才允许提示“继续分析”。
- 用户要求整合：当轮必须完成既有批次自检和分类合并；存在满足提示词修改门禁的样本时继续生成候选全文、
  执行 `[S3]` 并在校验成功后输出服务端原样 Diff，不存在时输出固定无修改整合结果。不得只输出
  整合计划，也不得在无提示词缺陷时调用 `[S3]`。
- 用户确认写入：只有已展示最终 Diff 时才执行 `[S5]`，不得为各批次分别写入。

## 服务端续批凭证

首批查询成功后，任务、Prompt、验证集、规则组、操作人、本地会话、过滤条件、分页大小、下一页和结果快照
由 `tool_query_validation_result` 响应中的 `data.data.continuationToken` 在服务端加密绑定。模型不得
维护本地续批锁，也不得自行计算下一页。

用户说“继续分析”或“下一批”时：

- 只允许当前用户消息紧邻上一条成功的“验证任务 Badcase 阶段分析”助手回复；该助手回复对应的工具
  响应必须满足 `data.data.page.hasMore=true` 且 `data.data.continuationToken` 非空。满足时只按统一
  流程 `[B1]` 续批调用合同原样回传 Token。
- 上一批阶段分析之后只要出现过其他用户消息，Token 就永久失去续批资格；即使用户随后回复“继续
  分析”、粘贴 Token、任务 ID、页码或要求恢复旧任务，也不得使用历史 Token。此紧邻门禁与 Diff
  确认门禁一致，不得根据语义相关、会话历史或模型记忆放宽。
- 阶段分析必须按固定模板原样展示本批 Token；除此之外禁止解析、摘要、改写、拼接或伪造 Token，
  也禁止用历史输出中的 task/prompt/dataset/ruleGroup/page 替代 Token。
- 非紧邻、Token 缺失、不可取或工具返回 Token 错误时立即停止，回复
  `续批凭证缺失、已失效或不是紧邻续批，已停止继续分析；请通过页面的「一键分析 Badcase」按钮重新发起。`
- `has_more=false` 时固定回复
  `本任务 Badcase 已全部分析，无下一页；如需汇总结论，请回复「整合修改建议给我一个草稿」。`

**整合修改建议**不使用 Token 查询下一页；只合并当前会话中已完成且身份一致的阶段分析。至少存在
  一批完整阶段分析，就允许整合。`has_more=true` 时也可整合，但必须如实保留未分析数量和回归风险；
`has_more=false` 时正常整合全部已分析结果。整合前仍必须核对各批可见输出中的 task/prompt/dataset/ruleGroup 一致；
任一批身份不一致时停止整合。

## 查询与判断

1. 从入口的 `badcaseRouteContext` 反校验 `validationCaseId<=0 && validationTaskId>0`，再重新读取
   本轮业务上下文并锁定 `badcaseMode=TASK`；只要上下文 `validationCaseId>0` 就立即停止并重新路由
   SINGLE，禁止因用户文字像整任务请求而继续。首批使用当前业务上下文建立服务端凭证；续批只使用上一批
   工具响应的 `data.data.continuationToken`；续批前还必须通过“服务端续批凭证”的紧邻门禁。
2. 首批或“继续分析”按统一流程 `[B0]`～`[B3]` 完成入口校验、本页验证结果查询、基础版本锁定、
   Case 去重，以及本页类目去重后的规则和 CDN 查询；必要映射在 `[B4]` 逐条确定核验范围后按类目去重查询。所有 MCP 名称、参数和响应门禁只
   以统一流程为准，本入口不复制、删减、改名或绕过。
3. 按 `[B4]`～`[B6]` 对本批每条样本建立证据并选择唯一一级分类，再统计各明确结论和证据不足数量；不得
   先按批次整体分类。
4. 阶段分析只执行 `[B7]` 的非写入分支，不生成 Diff、不调用写入 MCP；按 `[B8]` 使用“阶段分析”
   模板输出。有下一页时在“续批 Token”字段原样展示服务端 `data.data.continuationToken`，并供紧邻
   下一轮工具原样回传。
5. 用户要求“整合修改建议”时不查询下一页；合并同一续批身份下已完成的阶段结论并按下方“整合修改
   建议”执行。仅存在“是否修改提示词=是”的模型判得过严或过宽样本时生成一份完整候选提示词并执行一次 `[S3]`。

## 分批分析

每批结果只是当前会话中的阶段分析，不写入提示词表或 Diff 表，也不调用
`tool_edit_prompt_skeleton`。后续批次必须合并当前会话中同一任务、同一基础提示词的既有
阶段结论，不得把每批建议分别创建为草稿。非提示词缺陷不输出空 Diff；CDN 必须是最后一行。

````markdown
## 验证任务 Badcase 阶段分析
- Agent：`<名称；查不到时写ID>`
- 任务 / 验证集：`<task_id> / <dataset_id>`
- 基础提示词：`<名称>`（ID：`<PromptVersionBaseInfo.prompt_version_id>`）
- 续批 Token：<`hasMore=true` 时逐字符复制本批 `data.data.continuationToken`；`hasMore=false` 时写“无”>
- 批次：第 `<page>` 批
- Badcase：共 `<total>` 条，本批分析 `<analyzed>` 条，累计已分析 `<累计去重数>` 条
### 归因统计
| 一级分类 | 数量 | 处理 |
|---|---:|---|
| 合理的 SKU/SPU 粒度差异 | <数> | 排除出模型 Badcase，不修改提示词 |
| 非模型 Badcase：人工标签疑似错误 | <数> | 不修改提示词，交由标注侧复核 |
| 重点 Badcase：模型判得过严 | <数> | 定位错误否决原因并处理 |
| 真实 Badcase：模型判得过宽 | <数> | 定位错误放行原因并处理 |
- 待核验（标签不确定）：<数；记录人工或模型哪一侧不确定，复核为明确标签后重跑>
- 待核验（证据不足：暂时无法归因）：<数；列出缺失的 SPU 口径判定证据并补证后重跑>
### 明细
| Badcase ID | 标签字段原值及映射 | 一级分类 | SKU/SPU 口径与关键证据（快照事实 vs extracted） | 具体原因与建议 |
|---|---|---|---|---|
| `<case_id>` | `human_label=<值>`（<映射>），`model_label=<值>`（<映射>） | <明确结论之一；未通过门禁时写对应“待核验”> | <比价项：快照事实 / 左右 value / match> | <具体原因与建议> |
### 本批候选修改
- 缺陷与样本：<仅“是否修改提示词=是”的模型判得过严或过宽样本及 case ID>
- 候选建议：<待最终整合的规则修改；无缺陷写“本批无提示词修改建议”>
- 不写入提示词：<合理粒度差异、人工标签疑似错误、两种待核验结果，以及原因不在提示词的真实 Badcase>
- 与前批关系：<新增/重复/补充/冲突；首批写“首批”>
- 分页状态：<`hasMore=true` 时写“本次已分析 <analyzed> 条，剩余 <remaining> 条”；否则写“本任务 Badcase 已全部分析”>
- 下一步：<`hasMore=true` 时固定写“请直接回复「继续分析」查看下一批”；`hasMore=false` 时固定写“已无下一批；如需汇总已分析结果，请回复「整合修改建议给我一个草稿」”>
- 整合状态：<累计存在“是否修改提示词=是”的样本时写“可回复「整合修改建议给我一个草稿」”；否则写“当前累计无可整合的提示词修改建议”>
验证集报告：[查看 CDN 报告](<真实链接>)
````

无链接时最后一行写：`验证集报告：当前验证任务未返回 CDN 报告链接`。

### 阶段分析输出硬校验

发送前逐项检查；任一项不满足就在内部重组回复，不向用户展示错误版本：

1. 第一行必须严格等于 `## 验证任务 Badcase 阶段分析`，模板前后不得添加文字。
2. 必须保留模板全部字段、三级标题、表头和顺序；禁止输出任务概览、耗时、Token、自由发挥的
   下一步说明或模板中不存在的段落。
3. 输出前必须存在本轮真实 `tool_query_validation_result`、`tool_query_cdn_report`，以及本页去重后
   每个 `category_id` 对应的规则/必要映射查询；缺任一必需记录只返回该步骤真实错误。
4. “续批 Token”必须来自本批工具响应；`hasMore=true` 时必须逐字符复制本批非空
   `data.data.continuationToken`，不得省略、脱敏或改写；`hasMore=false` 时必须写“无”，禁止展示
   历史 Token。
5. 各明确结论数量与“待核验（标签不确定）”“待核验（证据不足：暂时无法归因）”数量之和必须等于本批去重后的明细数；
   两种待核验结果都不属于新增一级分类。明细按
   `validation_case_id` 去重；`total`、
   `has_more` 和剩余数量只能由 `data.page` 计算，不得根据摘要或历史回复猜测。
6. 阶段分析不得出现 Diff、`diff_id`、S3 成功话术、确认创建话术或写入操作；候选修改只能作为
   待整合结论。
7. `分页状态`、`下一步` 和 `整合状态` 必须按模板给定条件各选择一个固定句式，不得保留条件占位符。
   只有本批响应 `data.data.page.hasMore=true` 且 `data.data.continuationToken` 非空时，“下一步”才允许
   出现“继续分析”；否则禁止输出任何续批提示。
8. CDN 行必须是最后一行；有链接只用真实 `tool_query_cdn_report.data.report_cdn_url`，无链接使用
   固定无链接文本。

## 整合修改建议

用户要求“整合修改建议给我一个草稿”时：

1. 只合并当前会话中任务 ID、验证集 ID 和基础提示词 ID 均一致的阶段分析；按
   `validation_case_id` 去重。整合前自检各批阶段结论是否完整可见；任一批次不可见时，
   必须用同一任务 ID、同一 `PromptVersionBaseInfo.prompt_version_id` 和原 `page.page_no` 重新查询该页，
   不得跳过也不得凭记忆补写。
   执行整合前必须核对所有阶段记录的 task/prompt/dataset/ruleGroup 一致；不一致时禁止整合。
2. 合并指向同一规则的重复建议；结合商品快照证据、`extracted` 抽取结果、比价规则和映射
   处理冲突。合理粒度差异、人工标签疑似错误、两种待核验结果及具体原因不在提示词的真实 Badcase 不得写入提示词。
3. 若合并后没有“是否修改提示词=是”的样本，按统一流程 `[B7]` 不执行 `[S3]`，只能使用下方
   “无修改整合结果模板”。若存在满足门禁的样本，将同一续批身份下的缺陷记录合并后交给 `[B7]`，只生成一份候选完整
   提示词并执行一次有效 `[S3]`；最终 Diff 和失败处理完全按 `[B7]`，不得自行书写或另造校验流程。
4. 存在满足提示词修改门禁的样本时，完整读取 [edit-skeleton-workflow.md](edit-skeleton-workflow.md) 的“输出硬
   校验”，复用其 Diff 原样复制、非零 Diff ID 和确认话术门禁，但必须使用下方“提示词缺陷整合提案
   模板”展示，保留 Task、Dataset、批次、Badcase、分析进度和同任务最近一次 CDN 查询结果。
   模板外不添加文字，此时不得
   调用写入 MCP。

### 整合输出硬校验

1. 无满足提示词修改门禁的样本时第一行必须严格等于 `## 验证任务 Badcase 整合结果`，完整保留上述模板
   字段和顺序，不得输出 Diff、S3 成功话术或确认创建话术；CDN 必须是最后一行。
2. 存在满足提示词修改门禁的样本时第一行必须严格等于 `## 验证任务 Badcase 修改提案`，完整保留专用模板
   的任务上下文、合理性判断、Diff 和确认话术；输出前必须存在本轮真实
   `tool_validate_prompt_skeleton` 成功调用记录，且必须通过 `edit-skeleton-workflow.md` 中适用于 Diff、
   Diff ID 和确认话术的全部硬校验。不得使用无修改模板或普通 EDIT 提案模板。
3. 两个分支都必须按 `validation_case_id` 去重，且任务 ID、验证集 ID、基础提示词 ID 完全一致；
   覆盖批次、Badcase ID、未分析数量和回归风险不得省略或猜测。
4. 两个分支的 CDN 行都必须是最后一行；有链接只用同任务最近一次真实
   `tool_query_cdn_report.data.report_cdn_url`，无链接使用固定无链接文本，不得在 CDN 后添加确认或解释。

## 确认创建后

只有最终整合结果存在满足提示词修改门禁的样本且用户紧邻确认，才执行 `[S5]` 的 EDIT 路径。
仅调用一次并创建一个新草稿，不为各批次分别创建草稿。本轮不再输出 CDN。
